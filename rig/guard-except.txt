# guard-except.txt -- symbols where rig/guard-check.sh PASS 1 flagged the
# pristine C body, and a human decided where the guard went.
#
# Format:  <symbol>  <reason>
#
# A line here is a decision, not a silencer. Each one says what pass 1 saw
# and why the port is still faithful. Adding a line without checking is the
# same defect the script exists to catch, one level up.

# --- branch hints inside a body that was ported whole ---------------------
#
# unlikely()/likely() is a hint to the branch predictor, not a guard: it
# changes no result. Where the WHOLE body moved to Rust, every branch it
# annotated moved with it, and only the hint is gone. Verified by reading
# both sides, not assumed.

minmax_running_max   likely/unlikely branch hints only; all four branches are in win_minmax_rs.rs running() (lines 108-117)
minmax_running_min   likely/unlikely branch hints only; same running() body, called with the reversed comparator

# --- an attribute on a definition nothing outside the file could see ------
#
# list_sort.c carried __attribute__((nonnull(2,3))) on the DEFINITION. It was
# never on the declaration in include/linux/list_sort.h, so no caller ever
# saw it and it constrained nothing outside that one translation unit; it let
# the compiler assume non-null while compiling list_sort() itself.
#
# It is a real loss and it is recorded as one rather than papered over: the
# Rust takes raw pointers and asserts nothing about them. Moving it to the
# header would make it apply to callers for the first time, which is a
# behaviour change upstream did not make, so it is deliberately NOT done here.
# The `likely(bits)` hit on the same body is a branch hint, reproduced as
# `if bits != 0` at list_sort_rs.rs:217.

list_sort            nonnull was on the definition only, visible to no caller; likely(bits) is reproduced at list_sort_rs.rs:217

# --- branch hints, again ---------------------------------------------------
#
# hex2bin's two `if (unlikely(hi < 0)) return -EINVAL;` guards ARE in the port,
# at lib/hexdump_rs.rs -- the whole body moved. What pass 1 matched is the
# `unlikely()` hint, which changes no result. Same case as win_minmax's.

hex2bin              likely/unlikely branch hints only; both -EINVAL guards are in hexdump_rs.rs hex2bin() (the `if hi < 0` / `if lo < 0` returns)

# --- A CONDITIONAL THAT WAS DELIBERATELY NOT REPRODUCED --------------------
#
# THIS IS NOT A FALSE POSITIVE. Pass 1 is right: the four siphash buffer
# entry points each carry
#
#     #if defined(CONFIG_DCACHE_WORD_ACCESS) && BITS_PER_LONG == 64
#
# and lib/siphash_rs.rs compiles only the #else arm, on every configuration.
# The #if arm reads the final partial word with load_unaligned_zeropad(): one
# word load that may run past the end of the buffer, made safe by an
# __ex_table entry that catches the fault. Reproducing it from Rust means
# emitting kernel exception-table entries from asm!.
#
# THE HASH IS IDENTICAL either way -- both arms compute the same `b`, and
# upstream's own lib/tests/siphash_kunit.c passes against the ported build.
# What is lost is one load instead of up to three on the tail. CLAUDE.md:
# performance is recorded, never a veto.
#
# Recorded in full in logs/deviations.md, with the fix shape. These four lines
# are the acknowledgement that the check saw it and a human decided, which is
# the whole point of this file.

__siphash_unaligned  CONFIG_DCACHE_WORD_ACCESS arm deliberately not reproduced; portable tail always. Same hash, slower. logs/deviations.md
__siphash_aligned    as __siphash_unaligned; and this symbol is not built on x86-64 at all
__hsiphash_unaligned as __siphash_unaligned
__hsiphash_aligned   as __siphash_unaligned; and this symbol is not built on x86-64 at all

__iowrite64_copy     CONFIG_64BIT fork reproduced as #[cfg(CONFIG_64BIT)] in iomap_copy_rs.rs; both arms present

# --- flex_proportions: a hint, and a guard reproduced via a differently-
# --- named retained thunk pass 1's same-name check cannot see -------------
#
# Both entries are genuinely accounted for; pass 1's `ported="$port/$rel"`
# same-symbol-name check just cannot see either shape. __fprop_add_percpu_max
# is the same likely()/unlikely()-hint-only case as errseq_check/blake2s_update
# above -- the `max_frac < FPROP_FRAC_BASE` condition it guards is reproduced
# in flex_proportions_rs.rs __fprop_add_percpu_max() verbatim, just without an
# unlikely()-equivalent hint (this project has no such hint construct, and the
# condition/consequence are what matters). fprop_local_init_percpu's
# raw_spin_lock_init(&pl->lock) is a REAL operation, not a hint, and it IS
# called -- via rust_flexprop_lock_init() (lib/flex_proportions.c), the
# retained C thunk raw_spin_lock_irqsave()'s whole family needs for the same
# reason as lib/ratelimit.c's rust_ratelimit_trylock_irqsave() (see
# logs/porting-hazards.md, "spinlock + IRQ state"): preempt_disable()/
# lockdep/qspinlock-slowpath baggage this port has no reason to reimplement.
# Verified by reading both files, and by the differential
# (port/test/flex_proportions/, ~6.9M cases, 0 fails) exercising it every run.

__fprop_add_percpu_max  unlikely() branch hint only; the `max_frac < FPROP_FRAC_BASE` condition it guards is in flex_proportions_rs.rs __fprop_add_percpu_max(), condition and consequence both intact
fprop_local_init_percpu  raw_spin_lock_init(&pl->lock) reproduced via rust_flexprop_lock_init() (lib/flex_proportions.c), a differently-named retained C thunk pass 1's same-symbol-name check does not look for
